# Linux 标准 EC 温度接口

`mechrevo_ec_sensors` 将已核对的两路 EC 温度接入 Linux hwmon，供 `sensors`
和其他标准监控程序读取。目前严格限定两种精确身份，不接受相似型号或其他 BIOS：

- MECHREVO `Kuangshi16Pro Series GM6PX0X` / `GM6PX0X` / BIOS `N.1.09MRO07`；
- MECHREVO `Jiaolong16K Series GM6BG0Q` / `GM6BG0Q` / BIOS `N.1.19MRO15`。

安装包含该模块的驱动包后：

```sh
sudo modprobe mechrevo_ec_sensors
sensors 'mechrevo_ec-*'
```

模块提供两路温度 (`temp*_input`) 和两路风扇转速 (`fan*_input`)，标签分别为
`CPU EC`、`GPU EC`、`CPU fan`、`GPU fan`。温度单位是毫摄氏度，转速单位是 RPM。
CPU/GPU EC 温度来自 `INOU.ECRR(0x043e/0x044f)`；风扇高字节为
`0x0464`/`0x046c`。GPU 转速低字节按机型区分：GM6PX0X 使用原厂方法中的
`0x046b`，GM6BG0Q 使用本机风扇扫频确认的 `0x046d`（`0x046a/0x046b` 在
全部转速下恒为 `0x41`）。读取沿用 Uniwill 固件的 ACPI ECRR 方法，并在成功
读取后等待 6–12 ms；不再依赖 TUXEDO 驱动导出的 EC 读取符号。
它们不是 `coretemp` 的 CPU 内部温度，也不等于 NVIDIA 驱动的 GPU 温度。
已有本机 WMI 与固件内存读取路径对照见[原厂分析](<../reports/GM6PX0X 原厂控制台静态分析 20261016.md>)。

模块不写 EC 地址、不设置风扇表或功耗，也不启动后台采样；只有读取属性时才调用
ACPI ECRR。探测时也只通过 ECRR 核对项目号和风扇能力位，不调用 ECRW。
通信失败返回错误，不复用旧值；大于 125°C 的字节返回 `ENODATA`，不显示成有效温度。
零度仍是允许的原始读值，不保证传感器已校准或设备健康。

只提供只读温度和风扇转速，没有写回调、PWM 或风扇百分比接口。
RPM 读取按高字节、低字节、高字节采样；高字节变化时最多重试三次，避免返回跨越
计数器回绕时拼出的明显错误值。EC 仍可独立更新，因此这不能保证原子快照。
注册前检查硬件身份、ECRR 项目/能力字段及四路传感器；失败时不留下半注册设备。
模块不依赖 TUXEDO 或 Uniwill 的私有内核符号，可单独加载和卸载：

```sh
sudo rmmod mechrevo_ec_sensors
```

模块包含精确的系统厂商、产品名、主板名和 BIOS DMI 匹配，不新增全局强制加载配置。
项目号不是 `0x10`、能力位不符、ECRR 不存在或初始传感器读取失败时，初始化会退出，
不注册 hwmon 设备。GM6BG0Q 的本机读数与扫频记录见
[硬件记录](hardware/GM6BG0Q.md#32-风扇转速与占空比)。
首次显式加载和运行读取需要实机核对；下次开机能否由系统自动加载应单独验收。

初版 r60 的 `modprobe -r` 实机测试曾连带卸载 WMI，导致平台重新绑定和 TCC
因短暂消失的键盘节点退出。已恢复 TCC；修正版去掉该软依赖，补充加载失败回归，
并重新验收模块卸载期间的 WMI build ID、平台设备与服务状态。

## 风扇模式冲突

现有 universal 风扇控制在 full fan 位已置位时，原先会跳过设速却返回成功。
现在返回 `EBUSY`，保留当前模式和风扇目标。调用者应提示模式冲突，不能将请求视为已应用。
此修复不新增曲线布局、档位或控制写入，也不证明原厂风扇策略已迁移完成。

## 2026-10-16 实机验收

安装 r61（源码 `726f9f2`），当前内核 `7.2.9-arch1-1`。标准 `sensors` 显示两路 EC 温度；
10 组读取中，两通道共 20 个 ioctl 值全部与前后 hwmon 值之一一致。
四个属性权限均为 `0444`；没有 PWM、风扇 RPM 或写回调。
修正版的加载、`modprobe -r` 卸载及重新加载通过；卸载后 hwmon 设备消失，
重新加载后仅有一个设备，WMI 与其他核心模块 build ID、键盘平台节点和服务 PID 不变。
新温度模块的运行 build ID 与安装文件一致。

7 项真实 C 回归覆盖身份、读取范围、单位、传输和模块加载失败、只读属性与清理。
故障路径使用模拟服务，不是本机固件故障注入。
另一个内核 `7.2.7-arch1-1` 仅验证编译安装，尚未启动验证；开机自动加载也尚未验收。
这些读数及卸载测试不能证明散热改善、原厂风扇迁移或长期稳定性。

## 2026-10-29 上游候选实机复核

由主线补丁源码构建的 `mechrevo-ec.ko` 在本机 `7.2.11-arch1-1` 通过 `W=1` 编译，
并与已安装驱动并行加载。首轮草稿因 ACPI 整数参数的 union 初始化错误而触发固件
参数警告、拒绝注册；修正为初始化 `integer.type` 后重新构建，设备注册成功并出现两路
温度和两路风扇只读属性。五组先后读取中，候选与已安装驱动的 CPU 温度都在 74–76°C，
GPU 温度为 45°C；CPU 风扇分别在 2469–2487 与 2478–2487 RPM，GPU 风扇均落在
4994–5250 RPM。读数不是同时采集，且传感器会变化，不能据此宣称逐值相同。

`modinfo` 显示候选无模块依赖。`rmmod` 后候选模块与 hwmon 节点消失，原模块和节点仍在。
这验证当前主板/BIOS 的加载、读取和卸载；不代表已安装此候选、开机自动加载、其他机型
或长期稳定性已验收。
